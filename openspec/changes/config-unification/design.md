# 配置统一化设计：逐步开放，而非两套版本逻辑

## 1. 使用场景与开关关系

一个公开QQ服务多个群和私聊账号，通常逐步增加功能，很少关闭。部署允许范围决定“可以提供什么”，各群/账号决定“现在给谁用”。功能包只是批量操作工具，不是额外权限层。

```
部署允许范围（启动配置）
├─ 群聊：本群开关
└─ 私聊：账号覆盖；缺行才使用私聊公共默认
```

群设置不约束私聊，私聊设置不约束群；账号单独开启可覆盖公共默认关闭，但不能覆盖部署禁止。积分、打卡和称号仍是账号全局数据，不改成按群分库。A群关闭后，用户在B群获得的历史数据仍存在，不把它误当成A群偷偷运行。

## 2. 配置契约与加载时机

### bot.allowed_plugins

- 缺键：为旧配置保留全部已安装插件的兼容模式，并给出“公开部署应明确配置名单”的启动提示。
- 显式列表：精确限定可运行插件；`[]` 不解释为全部，不能因空值扩大权限。与受保护系统组件冲突时启动失败。
- 值必须是字符串列表。未知插件、错用类名/name而非注册标识、其他类型均报错。
- 使用runtime_context.plugin_key的模块标识，如redeem_shop、weekly_quest，而不是shop_weekly_rotation、weekly_quest_reset。
- 公开模板使用明确名单；新增插件代码不自动加入名单。新增包成员也不自动写入任何群/账号开关。
- 配置只读，改部署名单需重启。本次不增加配置热更新。

加载分两步：core/config只读取及验证数据结构；所有插件完成自动导入后、start_panel和接收事件前，再校验注册名称、功能包、系统集合等引用并冻结策略。不能在注册表尚为空时把“全部插件”冻结为空。导入期禁止产生业务，禁用通过运行期授权实现，不另写社区导入分支。

### 系统组件

系统身份只免除所在群/账号的普通开关，不免除部署允许检查。生效的system_plugins（含缺省集）必须是allowed_plugins子集，冲突启动报错；公开模板将group_manager列为系统插件并在允许名单中保留，避免丢失管理入口。既有自定义system_plugins精确替换语义不另加隐藏成员。消息输出是核心模块，不是可被名单关闭的插件。公开模板显式给出匹配的system_plugins，不能忘记默认集合中仍包含私域插件。

### bot.feature_packs_file

缺失/空路径沿用现有内置包表；非空路径相对于主配置文件所在目录解析，也支持绝对路径。文件结构为包名到`{plugins: [注册标识]}`的映射，整体替换，不与内置表偷偷合并。空文件、非映射、坏YAML、缺文件、错误类型或未知插件均启动报错，不回退到更宽的内置表。显式空映射表示没有功能包，不改变单插件可管理性。

包表只定义集合，不定义默认开启集、不启动播种。管理展示基于包定义与部署允许范围的有效交集，空的有效包不提供开启操作；回执明确实际修改的插件，不能宣称禁止项已开启。默认表和外部表走同一路径。未来群审核播种另行设计，不借本提案自动开放功能。

## 3. 所有入口采用相同判断

- 普通消息、notice、request先检查部署许可，再按实际来源群/账号及系统保护判断。读取失败不得放开可选业务。
- 心跳没有天然群号，不调用普通私聊默认来推断范围；它只启动被部署允许的已声明任务，再按第4节检查任务对象。不是“去掉一行meta豁免”就完成。
- Operation同时保存部署许可与本次操作的局部快照。内部消费者必须先被部署允许，再检查局部启用；cleanup只可绕过局部新奖励开关，不能绕过部署禁止。
- 每次操作/每轮扫描固定授权快照；修改开关从下一次操作/扫描生效，不中断已经开始的短事务。管理提示说明该边界。
- 可只读历史数据及静态定义用于展示，不因此触发目标插件的新业务。所有跨插件写入必须检查目标能力或经已绑定所属插件的通知执行。
- 已知例子：卧底继续记录游戏战绩，但称号关闭时不发新称号；含称号的一次性兑换码在目标功能不可用时拒绝整次兑换，不核销、不发部分奖励，也不发明替代奖品。抽奖及商店称号商品沿用已确认的依赖拒绝规则。

### 关闭和历史结果

关闭操作只修改设置，不删记录、不回收余额或称号。此前已确认的“局部关闭后，主动撤回旧打卡仍撤销对应奖励”保持；部署完全禁止的插件则不能以历史撤销为由运行。若要取消局部撤销例外，属于额外行为变更，不在此处暗改。

## 4. 心跳逐项作用范围

任务归属必须明确写在注册信息或统一任务描述中，不能仅用是否继承TimedHeartbeatPlugin猜测。允许复用现有扫描函数，但检查要在写库、发奖、发送和消费去重标记之前；查询任务归属不等于执行业务。不得为每个群重复执行全局维护。

| 任务（所属插件） | 检查与范围 |
|---|---|
| 商店轮换（redeem_shop） | 货架全实例一份，部署允许时按原计划刷新一次；公告检查明确目标群的开关，无目标则不发，局部关闭不能让其他群货架停止 |
| 周常清理（weekly_quest） | 全局进度维护由部署控制；仍仅清理原先可清理的旧进度，不删除奖励记录、余额或历史成就 |
| 图片备份（backup） | 全局维护由部署控制，单次执行；通知按明确目标配置与系统保护规则，不猜一个群号 |
| 新闻（ff_news） | 当前配置的通知目标群需已开启，才抓取/发送；无有效目标不请求官网，不默默扩大发送到所有群 |
| 周报（weekly_report） | 当前明确目标群需已开启，才执行启动补查、聚合、保存和通知；不能先生成再只拦消息。本次不把固定单群服务扩成所有群周报 |
| 论坛（forum_notify） | 过期投票是全局维护，由部署控制；新帖公告另检查目标群。目标未启用时不发送也不把未通知帖子标记为已通知 |
| 闹钟（group_alarm） | 每条记录按群或私聊创建账号检查；关闭时不发送、不mark_fired、不advance |
| 活动计时（activity） | 已有跨群扫描逐活动检查group_id；关闭时不自动开始/取消、跳过成员、改截止状态或公告 |
| 仙人彩（immortal_lottery） | 已有按群开奖逐群检查；关闭时不开奖、扣返积分、改奖池或写结果；已收下注及未结算记录保留 |
| 启动公告（startup_changelog） | 同时受部署与目标规则约束；无许可不发送、不消费未发送标志。作为系统插件时局部免检仍须符合部署名单 |

没有单群上下文的全局维护是明确例外，不用群A的开关决定全实例状态。此模型不需要根据版名选择任务。

## 5. 恢复和积压：保留既有规则，不新造补偿系统

重点是逐步开放新功能，不增加暂停队列、自动退款或历史奖励重算。关闭期间不把任务删掉或伪装成完成；再次开启只从下一轮扫描开始使用既有到期判断。例如普通到期查询可能处理积压，仙人彩固定窗口可能已错过；不能一概承诺“都补跑”或“都作废”。

管理回执或可定位日志说明存在待处理/过期任务，特别是已收取费用但没有结算结果的记录。错过窗口仍保留可核查记录，由超级用户决定后续处置；本提案不擅自退款或创建新的开奖规则。重复执行保护沿用原业务唯一约束并补测试。后续如需统一补执行流程，另建提案。

## 6. 逐步开放与管理界面

复用现有/插件、/功能包的显式群与用户语法，只允许超级用户管理。群不开启则不自动使用默认包；私聊新账号仅继承已有公共默认。管理员可以固定公共默认为最小基础集合，对试用账号单独加功能；修改公共默认会影响所有继承者，回执必须说明，不能把批量影响藏在“全局”二字里。

允许名单不落库，旧群/账号行不清除。部署禁止项在查询中明确显示“部署未开放”，修改命令/API拒绝并不写开启记录；重新扩大部署名单可能使旧开启记录重新生效，启动日志应提醒这种情况，不承诺清空历史设置。功能包新增成员不自动产生DB开启行。

web_panel目前直接读注册表和数据库，并没有功能包展示数据源。任务必须显式接入公共的有效状态查询和功能包查询/展示，不能假设改FEATURE_PACKS后界面自动完成。启动与面板保存配置共用纯校验函数，禁止继续使用过时的静态_REQUIRED全集。

## 7. 有效菜单与文案

建立结构化指令条目，每条声明所属插件、原有权限要求和文字，统一按本次操作有效集合渲染。帮助本身不能授予执行权限。用户只看到自己当前位置已开放的功能；超级用户的管理段遵守现有权限，不能按版名选另一套业务。

继续使用bot.text_pack加载机制，提供按插件/条目覆盖的菜单文案，覆盖只改文字、不改条目归属或执行权限。旧整段menu_text无法可靠按插件过滤：启动给出格式迁移警告并回退可过滤的内置菜单，不原样显示全部指令，不靠正则猜自定义文案的权限。缺少新文案条目仍回退内置。此兼容性变化必须写入CHANGELOG及迁移说明；旧配置文件本身不因此无法启动。

## 8. 与版名无关的校验与模板

删除_EDITIONS取值限制与按版名的必填集合，冷却缺省统一0（这里只配置，不实现频控业务）；公共模板显式填3。外部timeline/OneBot HTTP有URL才要求配套参数；webapp启动入口检查其真实需要的配置，bot单独运行不替webapp要求字段。配置检查函数可供面板使用，但不启动服务、不读写生产DB。

公开模板为可加载的候选配置，不是公开运营完成证明：允许打卡基础九插件及menu/group_manager/monitor，system_plugins对应裁剪；私域定制、经济扩展、尚未实现的register/group_review不列入。backup等全局运维功能在权限与通知配置明确后由超级用户选择开放，不默认提供给所有普通用户。内置功能包维持兼容，公开示例包只含打卡基础；配置所有其他运行参数仍来自主配置文件，不新增环境变量来源。

旧私有配置无需增加字段即可加载，但其原来“局部关闭仍运行后台”的行为会被修正。实际提供的功能和模板不同，执行规则相同。全实例数据仍分库部署，不迁移私域数据到公服。

## 9. 交付与风险

先统一许可/校验及引用验证，再迁移心跳与已知旁路，再完成菜单、管理展示和模板。暂停中的community-feature-packs不并行实施。每个新增能力使用自己的spec.md，修改正式能力也写在对应目录。

关闭配置错误不得降级为全开；长时间任务遵守启动时快照，不宣称能立即中断。全局维护与局部业务的区分、恢复时原有到期规则、旧整段菜单回退都是本次必须向管理员说明的行为边界。实施中发现无法按此明确实现的任务，先修订提案，不再用私有/社区分支临时绕开。
