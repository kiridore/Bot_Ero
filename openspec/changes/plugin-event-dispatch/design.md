# 设计：插件同步通知与统一消息输出

## Context

已核查 main.py：on_message 为每个非 echo 外部事件创建线程，plugin_pool 在该线程顺序遍历插件，不是每个插件一个线程。checkin 直接调用称号评估、周常推进和商店道具；lottery 直接调用周常和称号；两撤回插件直接调用周常回退。

已核查两撤回插件及 core/db/titles.py、quest.py：撤回打卡不删除称号；周常撤奖只改变本周领取状态，不减少累计完成和历史全清次数。奖励标记与积分目前分别提交，必须修复其部分成功风险。

参见 proposal.md 的所有者授权：本次允许私有插件关闭语义改变，但不授权其他玩法变化。此前“注册式通知不可行”的结论不成立：插件加载时可以注册处理函数，运行时再按所属插件的设置决定是否执行。

## Goals / Non-Goals

目标：插件无需导入其他插件业务函数；新奖励遵守开关；历史奖励可正确撤销；消息有统一归集位置；保持原事件线程模型。

非目标：后台消费、Redis/RabbitMQ、跨进程广播、重启后恢复待发消息、自动业务重试、改变奖励价格概率、删除旧插件、改社区功能开放清单。时间线 HTTP 上报不是 QQ 提示，不在“全部消息发送迁移”范围。

## Decisions

### 1. 一次外部事件一个处理对象

拟新增 core/plugin_dispatch.py：每次 plugin_pool 建立独立处理对象，含操作标识、来源账号/群、开关快照、待处理通知和待发送请求。显式传给插件，不能把可变列表放在全局，也不能跨事件保存在插件实例。

使用当前线程内的列表或 deque 顺序处理，不为消费者起线程、不递归直接调用消费者。通知含类型、稳定来源标识、实际业务记录标识和必要数据；先完成来源数据写入，再发布完成通知。通知不传递正在使用的数据库连接给其他线程。

订阅注册表关联通知类型、所属插件标识、处理函数、执行顺序及是否属于旧奖励撤销。注册不代表启用。新业务按开关快照筛选，历史撤销按已有奖励记录筛选。系统级必需组件不提供账号关闭选项。

处理顺序与文本显示顺序分开。凡称号判定依赖某项统计写入，必须在对应统计完成后处理，并通过现状对照测试保持原有时机，不因此次重构提前解锁。运行时限制通知循环：同一来源通知不得无界重新投递自身；异常循环停止相关处理并记录错误，不拖死事件线程。

### 2. 通知不是只给奖励用

第一阶段通知包括打卡保存完成、打卡撤销完成、抽奖结果已保存，以及必要的处理完成通知。来源中包含消息及数据库记录标识，单条消息多图、一次一键抽奖多次抽取必须能区分。

打卡不调用称号/周常/商店函数；这些插件订阅通知后按自己的规则产生结果。月全勤积分属于打卡自己的奖励规则，使用共享积分服务，而不是创建“积分总开关”。需要在多个位置运行的逻辑可订阅不同的明确阶段通知，不把所有处理强塞到一个位置。

同一源操作中的后续通知继承操作标识、接收上下文和开关快照。一键抽奖的子结果继承同一输出范围，但各次抽取有独立业务标识，防止奖励误去重。

### 3. 私聊账号设置与权限

保留 group_plugin_config 的现有群/编号 0 私聊公共设置。新增账号覆盖表（user_id、plugin_name、enabled，联合唯一；不存在=沿用默认）。明确关闭必须保存 false，不能以删除代替；恢复默认删除覆盖行。

群聊只看群设置，私聊优先账号覆盖再查公共设置，无开启记录按现有规则视为关闭。读取一次快照供整个操作使用，不因处理期间改开关而执行一半功能。

扩展 /插件 和 /功能包 的目标语法，明确使用“群 <群号>”“用户 <账号>”；用户目标支持“默认”。保留旧指令形式，旧私聊无目标仍作用于私聊公共设置。只有超级用户能修改，包括账号本人的设置；若存在其他修改入口也必须执行同一权限检查。

名称解析复用现有插件标识，中文示例不意味着自动新增别名。系统组件和部署未开放的功能不得通过账号覆盖绕开原有约束；本提案不自行决定社区开放表。

### 4. 输出模块

拟新增 core/message_output.py，接受接收方类型与编号、消息内容、可选合并标记、显示顺序、提交序号。消息内容复用现有消息段，不更改 OneBot 协议。

处理函数的输出暂存，函数成功完成后才交给本次操作；同时提交的子通知也遵守这一规则。普通文本按（操作标识、接收方、非空合并标记）分组，再按显示顺序/提交序号稳定排序，以换行连接。未标记文本单发；含图片、转发、回复或其他特殊段的请求保持原结构，不当成普通文本粗暴合并；最终长度限制通过底层现有能力处理或有边界测试的拆分，不能截断丢内容。

全部内部通知处理结束后输出模块统一调用底层发送。旧插件在过渡期可继续调用现有 API；已迁移插件不得同时从新旧两条路径发送。输出模块不可关闭。发送失败记录原操作及目的地，不重跑业务、不自动重发结果不明请求。

### 5. 失败范围和数据库事务

一次打卡与每个奖励处理分别完成，不使用覆盖整个事件的长事务。消费者失败后继续其他独立消费者；依赖失败消费者的子通知不发布。失败提示不包含异常堆栈或用户敏感内容。

需要奖励事务的处理函数先算出计划，再在短事务中提交条件领取状态、奖励记录、积分变更及相关统计；这些操作不得各自 commit。失败回滚本次奖励事务，不回滚已经成功保存的打卡。外部 HTTP 或文件写入无法靠 SQLite 回滚，不得声称所有副作用都能撤销；发奖事务内不执行外部发送。

### 6. 奖励记录与并发

拟在 core/db/_base.py 增量建表，并在 core/db/rewards.py 集中处理：业务奖励标识、所属插件、账号、来源操作、规则/周期、来源位置、数额、发放/撤销状态及时间。奖励标识按真实业务唯一性构造，而不是仅靠一次外部消息的随机 ID。周常奖励的唯一性是账号/任务/周/本次有效领取，不是每张图片一份。

同一业务可在撤销后合法重新达标，需要记录新的领取次数或等价的历史记录，不能用永不释放的唯一键阻止再领取。撤销条件依据剩余打卡记录和规则计算，不能把导致达标的某一张图片当成奖励的唯一依据。

唯一约束、条件更新、同一事务保证不同事件线程不会重复发奖/重复扣分。撤销后积分不足的处理保持现有扣分规则，不擅自改为截断到零。奖励记录不因任务进度例行清理而一并丢失。

旧数据不补造精确来源。必须明确区分当前有效的新领取和旧领取，不能以“曾有历史新记录”替代判断；新记录已撤销、随后旧网页入口重新发放的同周期领取仍须扣回。旧路径只处理当前未接管的领取，避免双扣。保留旧全勤/周常撤销条件、称号拥有记录以及累计成就规则。

实现核查补充：新增 plugin_reward_reversals，以插件/账号/奖励键/撤回来源为联合主键记录真实扣回，与领取状态和余额同事务；这样重复的旧撤回通知不能扣掉后来重新领取的奖励。记录旧领取的实际撤销不等于补造旧发奖历史。

全勤奖励也由 checkin.completed 的独立消费者处理，失败不阻断其他奖励；两种撤回共用 checkin.retracted 的全勤清理消费者。保留原有本周首次条件、业务周08:00与自然周/月00:00口径，不在事务改造时修订数值或条件。

## Risks / Trade-offs

- 同步处理仍可能被慢插件阻塞 → 本次只解耦，不承诺延迟降低；不引入未经确认的异步执行。
- 同一用户在多个群同时操作 → 用数据库事务及业务唯一约束，而非仅用进程锁。
- 开关从“关闭指令”变为“停止新业务” → 私有和社区都测试，版本说明明确授权变化。
- 新旧发送方式并存可能重复回复 → 每个迁移入口有发送次数断言，逐文件迁移清单追踪。
- 全勤和周常撤销代码部分重复 → 可提取共享计算以保证两种撤回方式一致，但不得顺便修订自然周/周一08:00等既有玩法边界；发现冲突单独记录。

## Migration Plan

第一阶段按 tasks.md 实现：基础机制 → 设置与事务 → 核心插件迁移 → 集成验收。上线前备份数据库，迁移只新增表/必要索引，不删历史记录。已写入新奖励记录后回退旧代码可能失去防重复保证；回退必须停止机器人、备份并验证数据兼容，不能宣称直接 git reset 安全。

后续阶段必须继续：卧底游戏及其称号通知；其余普通命令与图片/转发发送；定时任务和系统插件的发送。第一阶段创建 migration.md 的全量逐文件清单；后续分别创建 OpenSpec 提案并逐项验收。只有全部插件均经统一输出模块时才算整体迁移结束，本提案归档仅表示第一阶段完成。
