# 后续计划核查：部署只通过配置区分

## 结论与适用范围

所有者最新要求：社区和私有部署共用同一实现，只通过实际配置值决定行为，不允许按版本在插件中维护两套独立逻辑。这个要求也适用于配置加载、中央检查和权限判断，旧的“五处允许 edition 分支”不再是例外授权。

当前插件和通知框架未发现版本业务分支；core/config.py 仍按 edition 决定必填项与冷却默认值。旧社区计划有多项尚未实现的版本分支，必须修订后再实施。

本文件是计划审查与修订方向，不是新增功能已实现的证明。下述配置能力尚未落代码，具体配置键、默认值和兼容迁移须在对应 OpenSpec 提案中定义并验收；不要将建议字段当成已有接口。旧私有配置应保持可加载及既有行为，已明确授权的插件开关和消息合并变化除外。

## 当前重构提案是否需要重做

`plugin-event-dispatch` 不需要推翻。同步通知、消息输出、账号开关、奖励记录和撤销逻辑本来就对两种部署一致。

- 5.3 抽奖迁移继续按插件开关与实际能力处理，不加入任何版本判断；称号关闭时暂时禁止抽奖的既定规则对所有部署一致。
- 5.4 的周常/称号/商店输出迁移继续共用实现；未设置公告目的地则不发送，与版名无关。
- 阶段6必须记录当前配置加载的edition遗留差异；当前重构验收不能被表述成“整个社区版已完成配置化”。是否在本提案内扩大到配置加载改造需单独裁定，不能偷偷加入新范围。
- `community-feature-packs` 仍为暂停的旧草案；其中关闭积分、economy_active、双版包表等内容都不能继续实现。重启该任务前应重写提案，而不是解除暂停后照旧任务执行。

## 首版范围纠偏

已确认开放：打卡、消息撤回打卡、指令撤回打卡、补卡与管理员补卡、周打卡图、全部作品展示、本周名单、个人档案、积分排行榜，以及共用的积分余额和加减功能。

未开放经济扩展：抽奖与一键抽奖、积分商店、兑换码、批量发金币、周常任务和称号管理指令。不能因插件解耦完成就自动把这些加入社区首版。注册、群审核、黑名单及运维能力按原准入计划另外配置。

总计划批次1、T0.7默认包、T1.4审核播种仍写“基础+经济扩展”，均应改成只选择打卡基础。文案包目前仍有经济指令，需在首版装配时与真实开放范围同步。

## 应新增的共同验收规则

1. 同一份有效配置，仅更改或去掉部署描述标签，不改变必填校验、默认值、功能可用性、权限、奖励和事件处理路径。
2. 同一项能力在任意部署均可按相同规则启用/关闭；不把注册、审核、黑名单或频控硬绑定community。
3. 现有私有配置无需补一批新字段即可保持原有功能；允许的行为变化仅限已经确认的重构范围。
4. 配置明确禁用插件时，消息、请求、通知、心跳和其他插件发出的内部通知都不能产生该插件的新业务；历史奖励撤销保留既定例外。
5. 系统插件保护与部署禁用不得互相覆盖造成偷偷启用；冲突配置应明确报错或有已说明的统一优先规则，不得靠版名解决。
6. 群与账号开关不能重新开启部署未开放的功能；必需输出模块不允许被普通插件开关关闭。
7. 权限策略遵守既定超级用户硬限制；两模板相同权限配置时，同一账号得到相同结果。
8. 只更换配置模板即可部署；无长期版别代码分支，无按版名替换业务实现的工厂或隐藏策略选择。

## 推荐后续顺序

1. 完成当前通知重构5.3，再做阶段6完整验收。
2. 新建配置统一化提案，明确通用配置结构、旧配置兼容、插件全局允许范围与功能包数据化；同时修订旧T0.7草案。
3. 按通用配置实施注册、审核、黑名单、频控和权限；不使用版名条件作为省事替代。
4. 生成两份配置模板，纠正首版功能与文案范围，完成跨配置组合与实际部署验收。

所有涉及用户可见行为的后续变更仍须OpenSpec提案和独立验收。此次核查不修改运行代码，不替换已经通过测试的打卡/积分规则，不改变私有部署更新路径。
