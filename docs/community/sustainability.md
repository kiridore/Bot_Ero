# 维护者可持续性守则（公开版运营红线）

> **定位**：本文档是公开版的运营约束，与功能验收平级——每次开放新功能/新批次时，对照本文检查"这次变更是否增加了不可持续的维护负担"。
> **背景（2026-10-09，所有者原话）："公开之后没有熟人社区支撑，很容易失去热情变成负担。"** 个人免费服务的头号死因不是成本、不是竞品，是维护者燃尽。本守则的目的是把公开版设计成一个**不需要持续热情也能存活**的系统。

## 一、低维护架构（根本原则）

- **功能即维护债**：公开版每多一个功能 = 一份永久维护承诺。开放任何新功能前先问"我愿意为它修五年的 bug 吗"，答案犹豫就不开。
- **首版刻意薄**：打卡域起步，经济/娱乐包按批次渐进。薄不是因为做不动，是呼吸空间。
- **节奏硬限制**：公开版每季度至多一次功能更新；其余时间只修 bug。慢不是劣势，是防止 firefighting 燃尽。
- **自动化优先清单**（每一条都是把未来的救火往零压）：
  - [ ] 崩溃自动重启（进程守护）+ 异常隔离（一个插件崩不拖垮其他——已由 plugin-event-dispatch 交付）
  - [ ] 磁盘/内存/进程告警推送到维护者 TG（NAS 侧 Hermes 基础设施可承载）
  - [ ] 每日健康摘要一条（而不是需要主动盯）
  - [ ] 滥用自动化拦截：频控、黑名单、群数上限（W1/T1.4/T1.5 落地项）

## 二、低成本正反馈的固定渠道

热情的燃料是"被需要感"——把它做成自动送达，不靠维护者主动去翻：

- **每周统计播报**（周报插件的公开版形态）：本周 N 群 / M 次打卡 / 最长连续 XX 天——发给维护者 TG + 一个公开频道。这一条消息就是"还有人用"的证据。
- **用户反馈通道**：bot 内反馈入口，优质反馈/打卡成果图自动转发维护者 TG。
- 年度数据故事（热力图/档案卡）既是用户福利，也是维护者的成就感物料。

## 三、预期管理与"合法退出"设计

- **对用户明示**：注册引导与公告中写明"个人业余维护，响应以天计"——预先管理预期，避免失望用户成为燃尽催化剂。
- **降级路径预设计**（存在"有尊严的结束方式"，反而更敢长期投入）：
  - 只读模式：停止新提交，历史打卡/档案仍可查询
  - 数据导出：群主可导出本群数据自行迁移
- 收入预期锚定：赞赏/爱发电目标是**覆盖服务器成本 + 提供"有人在在乎"的正反馈**，不是营收。10 个稳定捐赠用户 = 达标。

## 四、熟人社区的保留（情感锚点）

- 私有版（小埃同学）持续运行，是维护者主场——公开版的幺蛾子在自己群里回血。
- 编外维护者：从 15 人内测用户中发展 2-3 名，帮看反馈、帮测版本、帮审拉群申请。不需要会写代码，"有人一起扛"本身就抗燃尽。
- 问卷（docs 内测调查）中"愿意内测/愿意拉群"的 affirmative 答案是编外名单的第一来源。

## 五、验收口径

- 公开版每个批次的上线检查表新增一栏：**"维护者可持续性影响"**——该批次是否新增了需要人工响应的流程？是否新增了监控盲区？是否可以再自动化掉一块？
- **终极指标**：公开版连续一周不需要维护者被动动手。达成即视为燃尽风险解除——系统不再需要热情，只需要偶尔的注意力。
