# 群审核操作与恢复

## 开启与日常审批

公开模板已配置`group_review.require: true`，默认包为`打卡基础`。旧配置不启用审核，已有私有群无需补登记。开启时必须将group_review、menu、group_manager同时列入部署允许名单及系统插件；默认包的成员必须全部允许提供。容量`community.max_groups`必须是正整数。

超级用户在**私聊**机器人执行：

1. `/待审`：显示申请编号、群号、邀请人、时间、是否已在群内、处理状态和远端结果。不会暴露审批凭证。
2. `/审核 123456 通过`或`/审核 123456 拒绝`。
3. 同群多条申请时，指定`/审核 123456 通过 7`（7是申请编号），不猜测也不批量同意其他凭证。

通过后该群开启配置包、收到欢迎公告。其他历史插件开关保留，重新批准旧群前后应以`/插件 列表 群 123456`核对，避免意外恢复旧功能。新账号的私聊设置不受群批准影响。

手动拉入的群同样待审，批准前不响应消息和群任务；审核也必须私聊进行。拒绝已在群内的申请不自动退群。普通成员的入群申请和进退群通知不属于本功能。

## 故障恢复（不直接修改数据库）

| QQ回执或状态 | 管理员下一步 |
|---|---|
| 远端明确失败，申请回到待审 | 修复QQ连接/检查邀请有效性后，再执行相同审批命令 |
| 批准结果未知 | 先检查QQ端机器人是否已在目标群，再执行相同“通过”命令；程序优先用入群通知或获取群列表确认，仅补本地登记，不重复同意邀请 |
| 结果未知且群列表查询失败或目标不在群 | 保持未激活；恢复连接并核对QQ端。不要反复尝试新的批准凭证；无法确认时联系维护者处理，程序不提供强制成功按钮 |
| 远端成功、本地登记失败 | 检查磁盘空间、数据库权限和日志，修复后再次执行原命令；只重试本地事务，不再调用已确认成功的远端操作 |
| 拒绝结果未知 | 保留待确认记录；群列表中没有目标不能证明拒绝已完成。需维护者结合QQ端核实，本次不提供不安全的强制结束或自动重试 |
| 欢迎/管理员通知发送失败 | 审批事实保留。用`/待审`及`/插件 列表 群 123456`核对；不要通过重复审批重发欢迎。统一输出日志含操作及目的地 |
| 容量用尽 | 已批准群和结果未知的批准都占名额。先核实未完成批准，或按实际资源调整容量后重启；不能通过丢弃记录释放未知名额 |

机器人离开群后停止该群业务，历史数据和开关不删除；再次加入需重新批准。部署被中断时遗留的处理中记录也按结果未知处理。

## 维护成本与上线条件

- 日常只需QQ审批，不增加公网Web页面、后台自动重试或新的数据库服务。
- 不确定的远端结果可能需要人工核实，这是防止重复审批、超额接入的代价；本次不承诺所有故障都能只靠一条QQ命令恢复。
- 自动化测试模拟邀请、拒绝、超时、本地事务失败和并发审批；真实QQ邀请、通知顺序及私聊可达性须在公开试运行前验证。
- 使用配置前备份数据库。测试隔离曾有缺陷，详见本提案验收记录；修复后的测试全部使用临时绝对数据路径。
