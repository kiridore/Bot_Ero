# 社区版：当前需求与开放范围

> 当前执行依据；按1.54.2交付重新核对。任务状态和验收证据见[开发清单](development-plan.md)。本文不保留已被取代的实施方案，历史内容可从Git和OpenSpec归档追溯。

## 1. 已确认的需求及设计原因

| 需求 | 当前规则 | 为什么这样设计 |
|---|---|---|
| 一个公开QQ账号服务多个群和私聊账号 | 同一实例内账号数据共享；群和私聊的插件设置分别管理 | 用户不因换群丢失档案与积分，运营者可以按对象分批开放 |
| 私域定制功能不向公开部署提供 | 部署允许名单决定上限，群/账号开关不能突破 | 防止误操作或升级代码后自动扩散新功能 |
| 两种部署只配置不同 | 同仓库、同实现；edition仅描述，不参与默认值、权限、准入或业务选择 | 不维护两套玩法，避免修复只覆盖一边 |
| 私有服务持续运行 | 每个主干提交兼容旧配置，未经授权不改变业务 | 私有部署的更新命令会拉取主干，不能等发布时才检查安全 |
| 逐群、逐账号缓慢增加功能 | 超级用户在部署名单内单独开放；功能包只是批量设置 | 控制缺陷影响范围，给用户学习时间；新增插件不等于自动开放 |
| 管理权限明确 | 插件查询/修改、群审核及批量发积分仅超级用户 | 不让某群管理者改变其他群/账号或全实例经济；不得按版名放宽 |
| QQ注册由用户主动开始 | auto_friend通过申请，welcome负责欢迎，register处理/注册及协议同意 | 职责不重复；添加好友不等于已同意协议 |
| 群接入由所有者批准 | group_review处理邀请和机器人自身进退群，通过QQ审批 | 手动拉群也不能绕过批准；保留故障证据，避免重复远端审批 |
| 关闭不追溯删除历史 | 停止新的业务，保留数据；历史撤销与恢复按已有正式规范 | 防止关闭插件导致数据或已付任务丢失，不再另造补偿规则 |
| 维护负担可持续 | 公开版每季度至多一次功能更新，其余修复问题 | 不以持续加功能维持运营；每次开放评估人工处理与监控成本 |

不同实例的数据库和媒体目录完全隔离，不把私有数据迁入公开实例。实例内部共享账号数据不意味着群内所有展示都有群隔离；名单、积分榜等展示范围必须向用户解释。

## 2. 首版功能范围（不得自动扩大）

### 提供的用户功能

| 功能 | 插件 |
|---|---|
| 打卡与积分基础结算 | checkin |
| 通过撤回消息撤销打卡 | checkin_recall |
| 指令撤回打卡 | roll_back |
| 周补卡、单日补卡及已有管理补卡入口 | remedy_checkin（公开权限待核对，见开发清单） |
| 本周打卡图 | week_checkin_display |
| 全部打卡作品展示 | all_checkin_display |
| 本周打卡成员名单 | week_list |
| 个人档案 | personal_records |
| 积分排名 | leaderboard |

积分是公共基础数据，不因经济扩展未开放而移除。已有指令的群聊/私聊限制仍保留，例如不能把列入包解释为每条命令在私聊都可执行。

### 首版不提供

- 抽奖及一键抽奖、积分商店、兑换码、批量发金币、周常任务、称号管理。
- 娱乐、活动、卧底游戏、群管理工具和跑团玩法：只列后续候选，不默认进入下一批。
- FF14新闻、仙人彩、消息日志及依赖消息日志的周报、私域人设功能：公开部署不允许。
- webapp、网页注册、邮件及其他平台服务：不属于公开首版。

注册、群审核、菜单、插件管理、必要备份和监控属于接入/运维功能，不借此加入经济玩法。注册或审核只开启配置指定的打卡基础包；改功能包文件本身不自动启用任何对象。

## 3. 当前流程

1. 添加好友：auto_friend自动同意；welcome按文案包欢迎。1.54.2已补齐公开模板welcome配置；已有部署须自行补齐，真实QQ送达仍需试运行。
2. 用户私聊/注册，收到协议及引导；/同意EULA后保存同意记录，为该账号开启基础包，按已确认规则发送资料卡。
3. 未注册私聊原则上仅允许注册与菜单入口；1.54.2已修复菜单调度标识及好友申请被注册检查误拦的问题，未放宽业务权限。
4. 群邀请进入待审；超级用户私聊/待审、/审核进行处理。手动入群也待审，只处理机器人自身生命周期，不审批普通群成员加入。
5. 批准后群登记与基础包开启同事务；普通业务仍受群开关限制。未批准群不运行业务及所属定时任务，生命周期必须能处理。
6. 超级用户按对象扩大或收回功能。私聊无目标列表查本人；公共默认须明确查询；无目标修改仍按旧规则修改公共默认，回执说明影响。

黑名单目前只有存储及群审核检查，完整消息/后台限制与管理入口仍未交付；冷却有配置但不代表已实施频控。

## 4. 上线与后续开放

| 阶段 | 完成条件 | 对应需求与原因 |
|---|---|---|
| M0 基础改造 | 已交付配置化、插件通知第一阶段、文案包和心跳控制 | 支撑同实现、不同配置，避免直接删插件破坏私有服务 |
| M1 准入及运营准备 | 补齐已知缺陷、黑名单/频控、首版权限与模板验证、跨对象验收 | 注册与审核可运行不等于防滥用已完成 |
| M2 小范围试运行及正式验收 | 同版本私有回归，公开真实QQ流程、备份恢复和升级验证，运营确认 | 模拟API测试不能证明真实邀请、消息送达和风控表现 |
| M3+ 按反馈选择功能 | 独立提案、独立验收、维护成本可接受且所有者批准 | 不把旧批次表当成自动承诺，遵守季度开放节奏 |

公开部署目标为固定版本升级；当前/更新仍拉取主干，解决前不能在公开部署无条件使用。部署方式、实际QQ后端和进程守护按现场确认，不因旧计划写过systemd或某个后端就视作已部署。

## 5. 执行边界

- 新的用户可见行为先OpenSpec提案，验收全绿后归档，版本/测试/规格/文案同次逻辑提交。
- bot保持同步多线程；match不写状态。频控在执行控制处设计，不能把时间戳写入match。
- 不新增版名分支；同配置只改edition标签应得到同样结果。
- 每次上线检查维护者可持续性影响，详见[守则](sustainability.md)。潜在自动化/数据导出等不等于本轮必须全部实现。
- 当前工作以[开发清单](development-plan.md)为准，历史架构和市场构想不是实施授权。
